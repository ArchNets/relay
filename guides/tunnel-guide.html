نصب Netrix و ساخت تونل بین دو سرور با ir_spoof

ir_spoof

با این راهنما نسخه مستقل Netrix 0.1.0 از ir_spoof رو روی دو سرور لینوکسی نصب می‌کنیم و یک تونل TCP و UDP راه می‌اندازیم. سرور A پورت‌ها رو می‌گیره و سرور B از داخل تونل به سرویس‌های خودش وصل می‌شه. برای شروع، tcpmux انتخاب ساده‌ایه؛ هر دو نوع ترافیک TCP و UDP داخل ارتباط TCP بین دو سرور منتقل می‌شن.

قبل از شروع

  • دو سرور تحت کنترل خودت، با لینوکس amd64 و glibc؛ مثل نصب معمول Ubuntu یا Debian. این باندل برای Alpine با musl نیست.
  • Python 3.10 یا جدیدتر، systemd و iproute2 روی هر دو سرور. برای باز کردن ZIP هم unzip لازم داریم؛ curl فقط برای تست HTTP پایین استفاده می‌شه.
  • دسترسی sudo و یک روش امن برای جابه‌جا کردن فایل محرمانه بین دو سرور، مثل SSH یا SFTP خودت.
  • روی سرور A، پورت TCP 4000 باید از سرور B قابل دسترسی باشه. اگر فایروال داری، همین دسترسی رو با ابزار همیشگی خودت بده. برای tcpmux لازم نیست پورت UDP 4000 رو باز کنی.
  • پورت‌های 18080 و 18081 روی A و 8080 و 8081 روی B باید برای این مثال آزاد باشن. SERVER_A_IP یعنی آدرس واقعی سرور A؛ این عبارت رو همون‌طور کپی نکن.

نصب روی هر دو سرور

فایل netrix-ir_spoof-complete-linux-amd64-0.1.0.zip رو روی هر دو سرور بفرست. روی هر سرور، از پوشه‌ای که فایل ZIP داخلشه این‌ها رو اجرا کن:

unzip netrix-ir_spoof-complete-linux-amd64-0.1.0.zip
cd netrix-ir_spoof-0.1.0
sha256sum -c SHA256SUMS
sudo sh netrix-ir_spoof-linux-amd64-0.1.0.run

بررسی SHA256 باید بدون خطا تموم بشه. نصب‌کننده فایل‌های داخل همین باندل رو بررسی می‌کنه و چیزی از سایت سازنده دانلود نمی‌کنه. بعد از نصب، اگر منو باز شد، گزینه 0 رو بزن تا خارج بشی؛ ادامه آموزش با دستورهای مشخصه. فایل SHA256SUMS سالم بودن فایل‌ها نسبت به همین بسته رو بررسی می‌کنه؛ اعتبار کسی که بسته رو ازش گرفتی رو به‌تنهایی ثابت نمی‌کنه.

netrix -version
python3 --version

روی A یک کلید خصوصی بساز

فقط روی A این دستور رو اجرا کن. یک کلید تصادفی محلی ساخته می‌شه؛ محتوای کلید توی خروجی چاپ نمی‌شه:

sudo netrix-manager secret demo
sudo stat -c '%a %U %G' /etc/netrix/secrets/demo.psk

قبل از انتقال فایل، روی B پوشه کلیدها رو با دسترسی محدود بساز:

sudo install -d -m 700 -o root -g root /etc/netrix/secrets

خروجی دستور دوم باید 600 root root باشه. فایل /etc/netrix/secrets/demo.psk رو با اتصال SSH یا SFTP خصوصی و دسترسی مدیریتی خودت به همین مسیر روی B منتقل کن. کلید رو توی تلگرام، پیام عمومی، اسکرین‌شات یا خط فرمان paste نکن. فایل روی A فقط برای root قابل خوندنه؛ با یک کاربر معمولی، کپی مستقیمش بدون دسترسی مدیریتی انجام نمی‌شه. اگر مسیر SSH خودت اجازه ورود root نمی‌ده، انتقال رو با روش مدیریتی امن خودت انجام بده؛ نیازی نیست ورود SSH با root رو صرفاً برای این آموزش فعال کنی.

بعد از انتقال، روی B مالک و سطح دسترسی رو تنظیم کن و چک کن:

sudo chown root:root /etc/netrix/secrets/demo.psk
sudo chmod 600 /etc/netrix/secrets/demo.psk
sudo chmod 700 /etc/netrix/secrets
sudo stat -c '%a %U %G' /etc/netrix/secrets/demo.psk

روی B دوباره secret demo رو اجرا نکن؛ هر دو طرف باید دقیقاً یک کلید داشته باشن. این PSK فقط برای احراز هویت و رمزنگاری بین سرورهای خودته و هیچ ربطی به لایسنس تجاری یا ثبت IP در سایت سازنده نداره. با --psk-file، مدیر به‌صورت پیش‌فرض رمزنگاری ChaCha20-Poly1305 رو فعال می‌کنه.

تونل سرور A رو بساز

روی A اجرا کن. پورت TCP 18080 این سرور به TCP 8080 روی B می‌رسه و UDP 18081 به UDP 8081 روی B:

sudo netrix-manager create demo --mode server --transport tcpmux \
  --listen 0.0.0.0:4000 --pool 1 \
  --psk-file /etc/netrix/secrets/demo.psk \
  --tcp-ports '127.0.0.1:18080=127.0.0.1:8080' \
  --udp-ports '127.0.0.1:18081=127.0.0.1:8081' \
  --health-port 19080 --start

آدرس سمت چپ هر mapping روی A باز می‌شه؛ آدرس سمت راست رو B به‌عنوان مقصد می‌بینه. پس 127.0.0.1:8080 یعنی سرویس محلی روی B، نه A. سرویس با اسم netrix-demo.service ساخته، شروع و برای بوت بعدی فعال می‌شه. تا وقتی B وصل نشده، داشتن سرویس فعال روی A به‌تنهایی یعنی تونل آماده نیست.

تونل سرور B رو وصل کن

روی B، SERVER_A_IP رو با IP واقعی A عوض کن و دستور رو اجرا کن:

sudo netrix-manager create demo --mode client --transport tcpmux \
  --peer SERVER_A_IP:4000 --pool 1 \
  --psk-file /etc/netrix/secrets/demo.psk \
  --health-port 19080 --start

اینجا B اتصال رو به A شروع می‌کنه. روی B mapping اضافه نمی‌کنیم؛ mappingها روی A تعریف شدن و سرویس‌های مقصد روی B هستن. پورت health روی هر سرور فقط روی loopback در دسترسه. چون اینجا دو سرور جدا داریم، یکسان بودن health_port مشکلی نداره.

وضعیت هر دو طرف رو ببین

روی هر دو سرور اجرا کن:

sudo netrix-manager status demo
sudo netrix-manager health demo
systemctl status netrix-demo.service --no-pager

برای دیدن خطای محلی سرویس، journalctl -u netrix-demo.service -n 50 --no-pager رو اجرا کن. اگر وصل نشد، اول IP و TCP 4000، یکسان بودن کلید، در دسترس بودن A از B و آزاد بودن پورت‌ها رو بررسی کن. لاگ و تنظیمات واقعی خودت رو بی‌دلیل عمومی نکن؛ خطای محلی ممکنه اطلاعاتی از تنظیمات اتصال داشته باشه.

TCP رو با یک سرویس آزمایشی چک کن

تونل خودش وب‌سرور یا سرویس مقصد نمی‌سازه. اگر روی B از قبل سرویس HTTP روی 127.0.0.1:8080 داری، همون رو تست کن. وگرنه روی B یک ترمینال جدا باز کن و این نمونه موقت رو با کاربر معمولی اجرا کن. فقط پوشه آزمایشی زیر سرو می‌شه، نه فایل‌های شخصی یا پوشه home:

mkdir -p /tmp/netrix-http-demo
printf 'Netrix ir_spoof tunnel OK\n' > /tmp/netrix-http-demo/index.html
python3 -m http.server 8080 --bind 127.0.0.1 --directory /tmp/netrix-http-demo

این ترمینال رو باز نگه دار. حالا روی A اجرا کن:

curl --noproxy '*' --fail --max-time 10 http://127.0.0.1:18080/

اگر Netrix ir_spoof tunnel OK دیدی، درخواست از A وارد تونل شده، به وب‌سرور محلی B رسیده و پاسخ برگشته. این فقط تست TCP/HTTP بود؛ UDP رو جدا تست می‌کنیم.

UDP رو هم جدا تست کن

روی B، یک ترمینال جدا برای این UDP echo آزمایشی باز کن. اگر خودت سرویس UDP روی 8081 داری، این نمونه رو هم‌زمان روی همان پورت اجرا نکن:

python3 - <<'PY'
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.bind(('127.0.0.1', 8081))
print('UDP echo ready on 127.0.0.1:8081', flush=True)
while True:
    data, peer = s.recvfrom(65507)
    s.sendto(data, peer)
PY

روی A این بسته رو بفرست و پاسخ دقیقش رو چک کن:

python3 - <<'PY'
import socket
message = b'Netrix ir_spoof UDP OK'
with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as s:
    s.settimeout(10)
    s.sendto(message, ('127.0.0.1', 18081))
    reply, _ = s.recvfrom(65507)
    assert reply == message, 'Unexpected UDP reply'
    print(reply.decode('ascii'))
PY

با دیدن Netrix ir_spoof UDP OK، مسیر UDP هم رفت‌وبرگشت شده. برای توقف سرویس‌های آزمایشی Python، داخل هر ترمینال B کلید Ctrl+C رو بزن. این نمونه‌ها فقط برای تستن؛ برای استفاده واقعی، سرویس اصلی خودت رو پشت تونل بذار.

تنظیمات کامل این مثال چه شکلیه

دستورهای بالا تنظیمات رو در /etc/netrix/demo.yaml با دسترسی 0600 ذخیره می‌کنن. قالب زیر یک مثال کامل JSON با همان رفتار است. LOCAL_PSK فقط جای‌نگهداره، نه کلیدی که باید واقعاً استفاده کنی. SERVER_A_IP هم باید عوض بشه. برای مسیر اصلی همین راهنما از --psk-file استفاده کن تا کلید رو در فرمان یا صفحه چاپ نکنی.

پیکربندی A:

{
  "mode": "server",
  "profile": "balanced",
  "transport": "tcpmux",
  "listen": "0.0.0.0:4000",
  "psk": "LOCAL_PSK",
  "encryption": {
    "enabled": true,
    "algorithm": "chacha20-poly1305"
  },
  "tcp_ports": [
    "127.0.0.1:18080=127.0.0.1:8080"
  ],
  "udp_ports": [
    "127.0.0.1:18081=127.0.0.1:8081"
  ],
  "health_port": 19080,
  "verbose": false
}

پیکربندی B:

{
  "mode": "client",
  "profile": "balanced",
  "transport": "tcpmux",
  "psk": "LOCAL_PSK",
  "encryption": {
    "enabled": true,
    "algorithm": "chacha20-poly1305"
  },
  "paths": [
    {
      "transport": "tcpmux",
      "addr": "SERVER_A_IP:4000",
      "connection_pool": 1,
      "retry_interval": 3,
      "dial_timeout": 10
    }
  ],
  "tcp_ports": [],
  "udp_ports": [],
  "health_port": 19080,
  "verbose": false
}

اگر بعداً می‌خوای JSON شخصی خودت رو وارد کنی، فایل رو با مالک root و دسترسی 0600 نگه دار، LOCAL_PSK رو در یک ویرایشگر امن با کلید واقعی مشترک جایگزین کن و با sudo netrix-manager check config.json بررسیش کن. برای ایجاد یک تونل جدید از sudo netrix-manager create NEW_ID --config config.json --start استفاده کن. نام NEW_ID رو با یک شناسه آزاد مثل demo2 عوض کن؛ فایل محرمانه کانفیگ رو عمومی نکن.

مدیریت روزمره

sudo netrix-manager stop demo
sudo netrix-manager start demo
sudo netrix-manager restart demo

هر دستور رو وقتی لازم داری اجرا کن، نه اینکه برای هر بار بررسی هر سه رو پشت سر هم بزنی. stop تونل رو متوقف می‌کنه ولی فعال بودنش برای بوت بعدی رو حذف نمی‌کنه. برای حذف کانفیگ و سرویس این تونل، روی هر دو طرف دستور زیر رو اجرا کن؛ فایل کلید جداست و این دستور لزوماً اون رو حذف نمی‌کنه:

sudo netrix-manager delete demo --yes

اگر دسترسی از بیرون A می‌خوای

این مثال عمداً پورت‌های forwarding روی A رو فقط به 127.0.0.1 بایند می‌کنه؛ پس یک برنامه روی خود A می‌تونه از تونل استفاده کنه. برای دسترسی کاربرهای بیرونی، باید آدرس bind سمت چپ mapping رو با تصمیم خودت به آدرس مناسب سرور عوض کنی؛ مثلاً 0.0.0.0:18080. بعد دسترسی فایروال و امنیت سرویس مقصد رو هم متناسب با کاربردت تنظیم کن. عوض کردن bind ممکنه سرویس رو عمومی کنه؛ مدیر خودش پورت forwarding یا فایروال عمومی رو برایت باز نمی‌کنه.

برای تغییر یک تونل موجود، اول stop، سپس create demo --replace همراه با تنظیمات جدید و --start اجرا کن. مدیر فقط تنظیمات و سرویس‌های متعلق به خودش رو تغییر می‌ده و واحدی که بیرون از مدیر ویرایش شده باشه رو بدون بررسی قبول نمی‌کنه.

درباره حریم خصوصی و سازگاری

این نسخه تماس با سایت سازنده، lookup عمومی IP، لایسنس و کش تجاری، telemetry و به‌روزرسانی خودکار نداره. اتصال به سرور مقابل و backendهایی که خودت مشخص کردی انجام می‌شه. این یعنی حذف تماس‌های اضافه؛ به معنی ناشناس شدن IP برای سرور مقابل یا اینترنت نیست. رمزنگاری محتوا رو محافظت می‌کنه، ولی اطلاعات شبکه مثل IP دو سرور همچنان برای مسیر ارتباط قابل مشاهده‌ست.

دو طرف این آموزش باید همین نسخه مستقل رو اجرا کنن. حالت پیش‌فرض از کلید تازه برای هر اتصال استفاده می‌کنه. استفاده با core اصلی موضوع جداگانه‌ایه و به حالت compatibility و محدودیت‌های گزارش سازگاری نیاز داره؛ برای TUN در آزمایش تعامل با core اصلی، یک queue پیشنهاد شده. این راهنما ادعای بازنویسی بایت‌به‌بایت یا برابری کامل با همه رفتارهای نسخه اصلی نداره. ۵۸ مورد تونل در محیط محلی لینوکس آزمایش شده؛ نتیجه شبکه واقعی تو به مسیر، فایروال و منابع سرورها هم بستگی داره.
